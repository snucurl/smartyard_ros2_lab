설치 시간은 별도 확보한다. 각 차시는 이론 20분, 코드 읽기 20분, 실습 60분, 점검·토론 20분을 기준으로 한다. 먼저 한 PC에서 실행한 다음 역할별로 분산한다.

터미널 규칙

  • PowerShell 표시는 Windows에서 실행한다. 방화벽·WSL 설치는 필요한 경우 관리자 창을 사용한다.
  • Bash 표시는 Ubuntu 22.04 터미널에서 실행한다. PowerShell에 ROS 명령을 붙여넣지 않는다.
  • 노드를 실행 중인 터미널은 그대로 둔다. 관찰·요청 명령은 새 터미널을 연다.
  • 모든 새 Ubuntu 터미널에서 cd ~/smartyard_ws 후 source scripts/env.sh 31을 실행한다.
  • 샘플은 1조의 도메인 31과 /yard01을 사용한다. 다른 조는 도메인을 32, 33 등으로 구분한다.
  • 작업별로 새로운 job_id를 쓴다. 같은 액션 서버 프로세스에서 이미 수락한 ID는 재사용할 수 없다.

이 모형은 매 실험마다 A→B 운반을 독립적으로 재현한다. 블록 재고·반납·복수 운반차 예약·경로 계획·가감속은 구현 범위 밖이다. 종결 상태의 busy=false는 다음 독립 실험을 받을 수 있다는 뜻이다.

1.2 노드·토픽·퍼블리셔·서브스크라이버

**노드(Node)**는 특정 기능을 맡는 실행 단위다. 한 프로세스에 여러 노드를 넣을 수도 있지만 이 교재에서는 이해하기 쉽도록 주요 노드마다 프로세스를 하나씩 사용한다. **패키지(Package)**는 코드·설정·빌드 정보를 묶는 배포 단위이며, **작업공간(Workspace)**은 여러 패키지를 함께 빌드하는 디렉터리다.

**토픽(Topic)**은 이름과 타입을 가진 데이터 흐름이다. 퍼블리셔는 데이터를 생성해 발행하고, 서브스크라이버는 관심 토픽을 구독해 콜백에서 처리한다. 1:1뿐 아니라 1:N, N:1, N:N 연결이 가능하다. 이름·타입이 맞고 QoS가 호환되어야 통신한다. 구독자가 없을 때 발행한 모든 메시지가 나중에 자동 복구되는 것은 아니다. 본 교재의 센서 토픽은 Volatile이므로 이후 수신되는 데이터부터 사용한다.

YardSensor의 중량 단위는 t, 풍속 단위는 m/s이다. stamp는 발행 시각을 기록한다. 여러 PC의 시각이 동기화되지 않았다면 현재시각 - stamp를 정확한 단방향 네트워크 지연으로 해석하지 않는다. 통신 단절 판정에는 수신 PC의 time.monotonic() 경과 시간을 사용한다. 단, 이것은 최근 수신 여부를 판단하며 센서 원천 데이터의 물리적 신선도를 완전히 보증하지는 않는다.

1.3 서비스와 액션을 구분한다

방식 통신 의미 실습 예 적절하지 않은 사용
토픽 지속적인 상태 전달 풍속·중량·장애물 단 한 번의 작업 완료를 데이터 반복만으로 추정
서비스 짧은 요청·응답 현재 운반 가능 여부 조회 30초 운반이 끝날 때까지 콜백을 점유
액션 장시간 목표 수행 운반·진행률·취소 목표 수락을 실제 완료로 오해
파라미터 노드 설정 관리 속도 설정·풍속 한도 고주파 모터 제어 명령을 반복 전달

서비스는 자체적으로 액션과 같은 진행률·취소 모델을 제공하지 않는다. 액션은 Goal 요청·수락, Feedback, Result, Cancel 절차를 가지며 내부적으로 토픽과 서비스를 활용한다. 선택 기준은 Humble 공식 가이드를 참고한다.

출발 조건은 다음과 같다.

가능 = 유효 경로 ∧ 최신 센서 ∧ 중량 ≤ 한도 ∧ 풍속 ≤ 한도 ∧ 장애물 없음 ∧ 최신 장비 상태 ∧ 장비 미사용

서비스 조회는 자원을 예약하지 않는다. 조회와 실제 Goal 도착 사이에 상태가 달라질 수 있으므로 액션 서버가 다시 검사한다. PC 4는 실행 중에도 센서 단절·중량·풍속·장애물 조건을 검사한다. 판단 노드와 운반 노드의 한도는 서로 다른 파라미터다. 기본 YAML에서 같은 값을 주지만 하나를 변경해도 다른 노드가 자동 변경되지는 않는다.

1.4 QoS와 발견

DDS의 발견(Discovery)은 통신 상대와 엔드포인트를 찾는 단계다. 실제 데이터 전달은 별도 단계다. “노드 이름이 보인다”는 사실만으로 모든 데이터 경로가 정상임을 보장하지 않는다.

데이터 이 교재의 QoS 이유
센서 Best Effort, Keep Last 5, Volatile 최신 표본 중심의 센서 흐름
장비 상태 Reliable, Keep Last 10, Volatile 상태 전달 재시도, 주기 5 Hz
서비스·액션 rclpy의 기본 프로파일 기본 요청·응답 프로토콜 사용

Reliable도 무한한 통신 장애를 극복하거나 완료 시간을 보장하는 뜻은 아니다. 애플리케이션 타임아웃이 별도로 필요하다. Best Effort 발행자에 Reliable 구독자를 연결하면 요구 품질을 충족하지 못하므로 매칭되지 않는다. 반대로 Reliable 발행자와 Best Effort 구독자는 호환된다. 공식 QoS 설명

1.5 파라미터의 소유권과 지속성

ROS 2 파라미터는 노드별로 존재한다. ros2 param set /yard01/transporter travel_speed_mps 0.5는 해당 노드의 서비스로 변경을 요청한다. 노드는 타입·범위를 검증하고 거부할 수 있다. /parameter_events에서 변경 이벤트를 관찰할 수 있다.

실행 중 변경은 자동으로 설정 파일에 저장되지 않는다. YAML로 내보내고 재시작할 때 읽어야 유지된다. set_parameters_atomically의 원자성은 한 노드에 대한 한 번의 설정 요청 범위이며 여러 PC 전체의 분산 트랜잭션이 아니다. 파라미터 공식 설명

02 · Windows·WSL2·Ubuntu·Humble 준비

2.1 Windows에서 먼저 확인한다

Windows 11의 mirrored 네트워킹을 기본으로 사용한다. Microsoft 문서의 최소 기능 조건은 Windows 11 22H2 이상이다. 실제 수업에서는 보안 지원 중인 Windows 11 버전과 업데이트된 WSL을 사용한다. Windows 10은 이 절차의 기본 지원 경로가 아니다.

# Windows PowerShell
winver
wsl --version
wsl --list --verbose

Ubuntu 배포판이 없으면 다음을 실행하고 안내되는 재시작과 Linux 사용자 생성을 완료한다. 기존 배포판을 삭제하지 않는다.

# 관리자 PowerShell: 최초 설치
wsl --install -d Ubuntu-22.04
wsl --update
wsl --set-default-version 2
wsl --list --verbose

성공 기준: Ubuntu-22.04의 VERSION 열이 2다. 이미 설치된 배포판이 1이면 wsl --set-version Ubuntu-22.04 2로 변환한다. 설치 후 Ubuntu에서 cat /etc/os-release가 VERSION_ID="22.04"인지 확인한다.

2.2 mirrored 네트워킹 설정

# Windows PowerShell: 기존 내용이 있으면 병합하여 편집
notepad "$env:USERPROFILE\.wslconfig"

[wsl2]
networkingMode=mirrored

기존 [wsl2] 절이 있다면 그 안에 설정을 추가하고 같은 절을 중복 만들지 않는다. 파일 이름이 .wslconfig.txt가 되지 않게 한다. WSL 내부의 /etc/wsl.conf와는 다른 파일이다.

# 모든 WSL 작업을 저장한 후 실행: 다른 WSL 배포판도 종료된다.
wsl --shutdown
wsl -d Ubuntu-22.04

mirrored는 멀티캐스트와 LAN에서 WSL로의 직접 연결을 지원한다. 그러나 방화벽·공유기의 단말 격리·학교망 정책까지 자동으로 해제하는 것은 아니다. 기본 NAT에 단순 TCP portproxy만 추가하는 방법은 본 교재의 DDS UDP 통신 해결책이 아니다. Microsoft WSL 네트워크 설명

2.3 실습 파일을 Ubuntu로 가져온다

제공된 smartyard_ros2_lab_v1.0.zip을 Windows 다운로드 폴더에 저장한다. ZIP의 최상위 디렉터리는 smartyard_ws다. Ubuntu의 Linux 파일시스템에 풀어 빌드한다.

# Ubuntu Bash
sudo apt update
sudo apt install -y unzip
WIN_HOME=$(cmd.exe /c echo %USERPROFILE% 2>/dev/null | tr -d '\r')
WIN_DOWNLOADS="$(wslpath "$WIN_HOME")/Downloads"
test ! -e "$HOME/smartyard_ws" && unzip "$WIN_DOWNLOADS/smartyard_ros2_lab_v1.0.zip" -d "$HOME"
cd ~/smartyard_ws
ls

smartyard_ws가 이미 있으면 위 명령은 기존 폴더를 덮어쓰지 않는다. 기존 작업을 보존한 뒤 새 빈 위치에서 진행한다. Windows의 다운로드 위치를 바꿨거나 WSL interop가 꺼져 있다면 ZIP의 실제 경로를 직접 지정하거나 파일 탐색기로 Ubuntu 홈 폴더에 복사한다.

예상 목록: src, scripts, docs, README.md, LICENSE, validation. 설치 전이라도 docs/index.html을 Windows 브라우저에서 열 수 있다.

2.4 Humble 설치

Ubuntu 22.04용 공식 apt 패키지를 사용한다. 시스템 Python을 기준으로 하며 실습 도중 Conda나 다른 Python 환경을 활성화하지 않는다. 아래 스크립트는 locale, Universe, 공식 ROS apt 설정, 시스템 업데이트, Humble Desktop, colcon, rosdep를 설치한다. 인터넷과 sudo 권한이 필요하다.

# Ubuntu Bash
cd ~/smartyard_ws
less scripts/install_humble.sh
bash scripts/install_humble.sh
source /opt/ros/humble/setup.bash
python3 --version
printenv ROS_DISTRO
ros2 --help

Ubuntu 22.04의 기본 Python은 3.10 계열이다. ROS_DISTRO=humble인지 확인한다. 설치 스크립트 전체와 apt 설정 이유는 이 문서 마지막의 소스 부록에서도 확인할 수 있다. Humble Ubuntu 설치 문서

문제 해결: ros2: command not found이면 새 터미널에 source /opt/ros/humble/setup.bash를 실행한다. apt 저장소 다운로드 실패는 인터넷·프록시·DNS를 확인한다. Python 모듈 오류가 나면 which python3와 echo "$VIRTUAL_ENV"를 확인하고 시스템 Python 환경으로 돌아온다.

생성된 package.xml, CMakeLists.txt, setup.py, setup.cfg, resource를 완성본과 비교한다. package.xml은 의존성, setup.py는 Python 모듈·리소스·실행 진입점, setup.cfg는 실행 파일 설치 위치를 정의한다. resource/smartyard_lab은 ament 인덱스에 패키지를 등록하는 표식이다.

3.3 인터페이스 생성은 왜 CMake 패키지인가?

.msg, .srv, .action은 Python 코드가 아니라 언어 독립 데이터 정의다. rosidl_generate_interfaces가 언어별 코드를 생성한다. Humble의 표준 방식에서는 이를 ament_cmake 패키지에 정의하고 Python 노드에서 import한다. 노드 로직은 모두 Python이다. 사용자 정의 인터페이스 튜토리얼

서비스의 --- 앞은 요청, 뒤는 응답이다. 액션의 첫 구간은 Goal, 두 번째는 Result, 세 번째는 Feedback이다. 액션 선언 순서가 Goal–Feedback–Result가 아님에 유의한다. float64는 부동소수점, bool은 참/거짓, string은 문자열이다.

# 관리자 PowerShell: ZIP을 푼 Windows 폴더에서 실행
# 아래 예시 주소를 실제 실습 LAN 서브넷으로 바꾼다.

스크립트는 해당 도메인의 DDS 포트 구간과 멀티캐스트 진단 포트 49150에 대해 지정 서브넷의 인바운드 UDP를 허용한다. 방화벽 전체를 끄지 않는다. 동일 이름의 기존 규칙은 보존하며, 서브넷을 바꾸려면 기존 수업 규칙을 제거한 뒤 다시 만든다. PowerShell 실행 정책으로 스크립트가 차단되면 학교의 실행 정책에 따라 관리자가 허용하거나, 스크립트 내용을 검토하고 필요한 명령을 관리자 창에서 직접 실행한다.

기본 RTPS 포트 계산에서 base = 7400 + 250 × DomainID이므로 도메인 31의 시작은 15150이다. 본 수업 스크립트는 1515015399를 사용한다. 도메인 32는 1540015649다. DDS 구현의 기본 포트 규칙과 소규모 프로세스 수를 전제로 한 수업 설정이며, 별도 전송 설정이나 매우 많은 participant가 있으면 재검토한다.

.\scripts\configure_firewall.ps1 -DomainId 31 -LabSubnet '192.168.10.0/24' -Remove

6.3 서버와 비동기 클라이언트의 관계

dispatch_checker.py는 수신한 최신 메시지를 저장해 두고 서비스 콜백에서 짧은 비교만 수행한다. 운반 시간 동안 기다리거나 상태를 예약하지 않는다.

self.service = self.create_service(CheckTransport, 'check_transport', self.check)
# 클라이언트: 응답이 도착하면 후속 콜백 실행
future = self.check_client.call_async(request)
future.add_done_callback(lambda f: self.checked(f, token))

call_async는 요청을 보내고 Future를 반환한다. 이후 spin이 응답을 처리한다. 구독/서비스 콜백 안에서 응답을 기다리는 동기 호출을 잘못 사용하면 교착 또는 다른 콜백 지연이 생길 수 있다. 본 관제 노드는 단계별 비동기 콜백으로 진행한다.

완료 체크: 서비스 요청·응답 필드를 설명하고, 정상 조회와 불가 응답을 확인한다. 서버가 없는 경우의 대기/타임아웃과 allowed=false를 구분한다.

07 · 액션 서버와 클라이언트 실습

7.1 액션 인터페이스와 직접 Goal

센서 기본값을 복원하고 PC 4가 미사용 상태인지 확인한다. 관제를 거치지 않는 직접 실습에서는 PC 4의 현장 조건 검사가 실행되지만 PC 3의 판단 서비스 호출은 생략된다.

# PC 2
ros2 action list -t
ros2 action info /yard01/transport_block
ros2 interface show smartyard_interfaces/action/TransportBlock
ros2 action send_goal /yard01/transport_block smartyard_interfaces/action/TransportBlock "{job_id: 'DIRECT_001', block_id: 'BLOCK_001', source_zone: 'A', target_zone: 'B'}" --feedback

예상 순서: Goal 수락 → 진행률 피드백 → 성공 상태 → success=true, reason='COMPLETED', moved_m=30.0, final_zone='B'. 실행·스케줄링 오차가 있으므로 소요 시간은 정확히 30.000초로 고정되지 않는다.

직접 보낸 Goal은 그 CLI 클라이언트가 소유한다. 관제 노드의 `cancel_job`은 관제가 보낸 Goal을 취소하는 명령이다. 위 직접 실습을 취소하려고 `cancel_job`을 호출하지 않는다. 이 교재에서 취소는 다음 절의 관제 경로로 실습한다. CLI 프로세스 종료 역시 서버 작업의 자동 취소를 뜻하지 않는다.

7.2 관제에서 시작하고 취소한다

아래의 start_job, cancel_job은 수업용 관제 조작 서비스다. 핵심 업무 서비스인 check_transport와 구분한다.

# PC 2: 새로운 작업 ID 설정
ros2 param set /yard01/control_center job_id ACTION_CANCEL_001
ros2 service call /yard01/start_job std_srvs/srv/Trigger "{}"

관제 로그에 GOAL_ACCEPTED와 Feedback이 나타나면 새 터미널에서 취소한다.

ros2 service call /yard01/cancel_job std_srvs/srv/Trigger "{}"

예상 결과: 요청 서비스의 CANCEL_REQUESTED → 취소 응답의 goals_canceling=1 → 최종 RESULT CANCELED: OPERATOR_CANCEL. 취소 요청 접수 자체가 최종 취소 완료를 의미하지 않는다. 이미 작업이 완료되었다면 취소 대상이 없거나 결과가 성공일 수 있으므로 다음 실험은 새 ID로 다시 시작한다.

7.3 액션 상태를 구분한다

상황 의미 확인 위치
Goal 거절 실행을 시작하지 않음 클라이언트 거절 응답, PC 4 REJECT 로그
SUCCEEDED 운반 완료 액션 결과, 장비 상태

7.4 동시에 두 작업을 요청한다

관제에서 새 ID로 작업을 시작하고 Feedback을 확인한다. 다른 터미널에서 직접 액션 Goal을 새 ID로 보낸다.

ros2 action send_goal /yard01/transport_block smartyard_interfaces/action/TransportBlock "{job_id: 'SECOND_WHILE_BUSY', block_id: 'BLOCK_001', source_zone: 'A', target_zone: 'B'}" --feedback

예상 결과: 두 번째 Goal 거절, PC 4에 VEHICLE_BUSY. 첫 작업을 취소하거나 완료시킨다. 첫 작업과 같은 ID를 나중에 다시 보내면 DUPLICATE_JOB_ID로 거절한다. 이 중복 기록은 프로세스 메모리 안에 있으며 재시작하면 지워진다. 영구적인 작업 이력 DB를 구현한 것은 아니다.

7.5 실행기와 동시성

transporter.py는 MultiThreadedExecutor(num_threads=4)와 액션용 ReentrantCallbackGroup을 사용한다. 운반 실행 콜백이 수행되는 동안 센서 수신·취소 서비스·파라미터 서비스를 처리할 수 있게 한다. 공유 상태는 RLock으로 보호한다. Goal 콜백에서 busy를 먼저 예약하므로 두 요청이 거의 동시에 도착해도 둘 다 수락하지 않는다.

운반 계산은 s_next = min(D, s + v × Δt)이다. time.monotonic()으로 경과 시간을 구하며, ROS 시뮬레이션 시간이나 실시간 제어 성능을 모델링한 예제는 아니다. Callback Groups 가이드

9.2 한 번의 지시로 전체 흐름 실행

ros2 service call /yard01/start_job std_srvs/srv/Trigger "{}"

관찰 순서

  1. PC 2의 요청 서비스가 success=true, REQUEST_QUEUED INTEGRATED_001을 반환한다.
  2. PC 3에 CHECK INTEGRATED_001: allowed=True reason=OK가 나타난다.
  3. PC 2에 GOAL_ACCEPTED가 나타난다.
  4. PC 4가 이동량을 계산하고 PC 2에 Feedback을 전달한다.
  5. PC 1·2·3이 장비 상태 토픽을 받는다.
  6. PC 2에 RESULT SUCCEEDED: COMPLETED가 나타난다.
  7. 장비 상태가 state=SUCCEEDED, busy=false, moved_m=30.0이 된다.

start_job의 success는 요청을 큐에 넣었다는 뜻이다. 이후 판단 불가·Goal 거절·운반 실패가 발생할 수 있으므로 반드시 최종 액션 결과를 본다. 센서 메시지가 반복되어도 작업은 자동 재시작하지 않는다.

9.3 속도 변경 실험

ros2 param set /yard01/control_center job_id SPEED_001
ros2 service call /yard01/start_job std_srvs/srv/Trigger "{}"

진행 중 약 10 m 지점에서 다음을 실행한다.

ros2 param set /yard01/transporter travel_speed_mps 0.5

이상적으로 처음 10 m를 1 m/s로 10초, 나머지 20 m를 0.5 m/s로 40초 이동하므로 합계는 50초다. 실제 변경 시점이 정확히 10 m가 아니면 값이 달라진다. Feedback의 이동 거리와 변경 시점을 함께 기록하고 T = s_change / 1.0 + (30 - s_change) / 0.5와 비교한다. 완료 후 속도를 1.0으로 복원한다.

9.4 판단 거부와 실행 실패를 분리한다

PC 3의 max_wind_mps를 8.0으로, PC 1의 풍속을 9.0으로 바꾼 뒤 새 ID로 start_job을 요청한다. 관제에는 DENIED: HIGH_WIND가 표시되고 액션은 시작하지 않는다. 이후 값을 복원한다.

반대로 PC 3은 10.0, PC 4는 8.0, 풍속은 9.0으로 설정하면 서비스는 가능으로 판단해도 PC 4가 Goal을 거부할 수 있다. 이것은 노드별 정책의 불일치를 보여준다. 세 값을 각각 기본값 10.0, 10.0, 6.0으로 복원한다. 실제 시스템의 일관된 정책 배포는 별도 설계가 필요하다.

11.1 저장소와 인증 준비

이 교재의 기준 저장소 이름은 smartyard_ros2_lab이다. 최초 업로드 담당자만 저장소를 만든다. 팀원은 같은 계정 비밀번호를 공유하지 않고 자신의 계정으로 접근한다. Private 저장소라면 필요한 사용자에게 저장소 권한을 부여한다.

계정 예시는 연결된 사용자 snucurl이다. 다른 계정으로 수업하면 아래 URL의 소유자를 바꾼다. 이미 원격 저장소가 준비되어 있으면 새 저장소 생성 단계는 건너뛴다. 이 교재의 업로드 명령은 학습자가 직접 수행할 수 있는 절차이며, 명령이 적혀 있다는 사실만으로 업로드 완료를 의미하지 않는다.

GitHub 웹에서 새 저장소를 만들 경우, 최초 로컬 파일을 올리기 쉽게 README·라이선스·gitignore 자동 생성을 선택하지 않고 빈 저장소를 만든다. 공개 범위를 검토하고 수업 준비 단계에서는 Private로 시작할 수 있다.

GitHub CLI로 인증하려면 Ubuntu에서 다음을 실행한다.

sudo apt update
sudo apt install -y gh git
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status

브라우저에 표시되는 본인 계정과 권한을 확인한다. 토큰·비밀번호를 소스파일이나 명령 예제에 기록하지 않는다. 개인 액세스 토큰을 코드에 넣거나 원격 URL에 포함하지 않는다.

12.6 확인 문제와 해설

Q1. PC마다 ROS_DOMAIN_ID를 다르게 주면 왜 통신되지 않는가?

도메인 ID는 컴퓨터 번호가 아니라 DDS 통신 그룹이다. 같은 조는 같은 값으로 설정하고 역할은 노드 이름·네임스페이스로 구분한다.

Q2. 서비스가 allowed=true인데 액션이 거절될 수 있는가?

가능하다. 서비스 조회는 예약이 아니며 시간 차이·장비 busy·서로 다른 노드의 파라미터·중복 job_id 때문에 액션 서버의 수락 조건을 충족하지 못할 수 있다.

Q3. Reliable을 쓰면 센서 타임아웃이 필요 없는가?

아니다. 연결 단절·프로세스 종료·장시간 장애가 있을 수 있다. QoS와 애플리케이션 수준 타임아웃은 서로 다른 문제를 다룬다.

Q4. Python 코드만 작성하는데 ament_cmake 패키지가 있는 이유는?

언어 독립 .msg/.srv/.action을 rosidl로 생성하기 위해서다. 생성된 Python 인터페이스를 ament_python 패키지의 노드가 사용한다.

Q5. 액션 클라이언트가 종료되면 서버도 반드시 멈추는가?

아니다. 별도의 취소·생존 감시 정책이 필요하다. 이 모형은 센서 stale 인터록은 구현하지만 관제 heartbeat 기반 중단은 구현하지 않았다.

Q6. 여러 PC의 stamp 차이로 정확한 통신 지연을 계산할 수 있는가?

공통 시각 동기화와 오차 평가가 없다면 어렵다. 이 모형은 각 수신 PC의 monotonic 경과 시간으로 최근 수신 여부를 검사한다.

Q7. start_job의 success=true가 완료를 뜻하는가?

아니다. 관제 요청 접수다. 서비스 판단, Goal 수락, 최종 Result를 이어서 확인해야 한다.

$creator = '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}'

def check_transport(request, sensor, sensor_age, timeout, max_load, max_wind,
                    vehicle_busy=False, vehicle_age=0.0):
    if not request.job_id.strip():
        return False, 'EMPTY_JOB_ID', 0.0
    distance = ROUTES.get((request.source_zone, request.target_zone))
    if distance is None:
        return False, 'UNKNOWN_ROUTE', 0.0
    if sensor is None or sensor_age > timeout:
        return False, 'SENSOR_STALE', distance
    if not math.isfinite(sensor.load_t) or not math.isfinite(sensor.wind_speed_mps):
        return False, 'INVALID_SENSOR_VALUE', distance
    if sensor.load_t <= 0.0 or sensor.wind_speed_mps < 0.0:
        return False, 'INVALID_SENSOR_VALUE', distance
    if request.block_id != sensor.block_id or request.source_zone != sensor.zone_id:
        return False, 'BLOCK_OR_ZONE_MISMATCH', distance
    if sensor.load_t > max_load:
        return False, 'OVERLOAD', distance
    if sensor.wind_speed_mps > max_wind:
        return False, 'HIGH_WIND', distance
    if sensor.route_blocked:
        return False, 'ROUTE_BLOCKED', distance
    if vehicle_age > timeout:
        return False, 'VEHICLE_STALE', distance
    if vehicle_busy:
        return False, 'VEHICLE_BUSY', distance
    return True, 'OK', distance

def advance(distance, speed, dt, total):
    if not all(math.isfinite(x) for x in (distance, speed, dt, total)):
        raise ValueError('non-finite motion input')
    if min(distance, speed, dt, total) < 0:
        raise ValueError('negative motion input')
    return min(total, distance + speed * dt)

def validate_value(name, value, rules):
    rule = rules.get(name)
    if rule is None:
        return True, ''
    kind, low, high = rule
    if type(value) is not kind:
        return False, f'{name}: expected {kind.__name__}'
    if kind is float:
        if not math.isfinite(value) or not low <= value <= high:
            return False, f'{name}: allowed range [{low}, {high}]'
    if kind is str and not value.strip():
        return False, f'{name}: must not be empty'
    return True, ''

            self, TransportBlock, 'transport_block', self.execute,

        with self.lock:
            allowed, reason, _ = self.eligibility(request)
            if self.busy:

                allowed, reason = False, 'DUPLICATE_JOB_ID'
            if not allowed:
                self.get_logger().warning(f'REJECT {request.job_id}: {reason}')
                return GoalResponse.REJECT

            self.busy = True
            self.job_id = request.job_id
            self.state = 'ACCEPTED'
            self.moved = 0.0

                        break
